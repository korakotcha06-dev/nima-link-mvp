# เทส Playwright — NIMA Link Module 2

เทส E2E ที่พิสูจน์ตารางสิทธิ์ใน `../ACL.md` ด้วยบัญชีทดสอบจริงบน Firebase ของจริง
**ไม่มี emulator ไม่มี dependency เพิ่ม** — ตามที่ทัชตัดสินใจไว้

## ไฟล์

| ไฟล์ | คืออะไร | สถานะที่คาดไว้ |
|---|---|---|
| `acl-ui.spec.js` | **ไฟล์ที่ 1** — เดินผ่าน UI จริง ยืนยันสิ่งที่ผู้ใช้เห็นตรงกับ ACL.md | ต้องผ่านทั้งหมด |
| `acl-db.spec.js` | **ไฟล์ที่ 2** — ล็อกอินผ่าน UI ก่อน แล้วยิง Firestore SDK ตรง ๆ จาก page context ข้าม UI ไปทดสอบกฎฐานข้อมูลโดยตรง | 🔴 ทำเครื่องหมาย `test.describe.fixme` ไว้ทั้งไฟล์ — จะยังไม่รันจนกว่า security rules รายคอลเลกชันจะขึ้น (ดู ACL.md หัวข้อ "บังคับใช้ที่ไหน") |
| `helpers.js` | ผู้ช่วยใช้ร่วมกัน — สมัคร/เข้าสู่ระบบ (idempotent), เรียก Firestore ตรงจาก page context | ไม่ใช่เทส ไม่มี `test()` ของตัวเอง |

**ไฟล์ที่ 1 เขียนจากตาราง ACL.md เท่านั้น ไม่ได้ลอกพฤติกรรมมาจากโค้ด `index.html`/`new.html`/`detail.html`** —
ตั้งใจให้เป็นด่านตรวจอิสระของฝั่งหน้าจอ ถ้าไปอ่านโค้ดแล้วเขียนตามที่โค้ดทำ เทสจะผ่านเสมอและไร้ค่า

## วิธีรัน

```bash
npm install        # ครั้งแรกครั้งเดียว
npm test           # รันกับเว็บจริงบน Firebase Hosting (baseURL ค่าเริ่มต้นใน playwright.config.js)

# หรือรันกับเครื่องตัวเอง (ต้องรันคู่กับเซิร์ฟเวอร์ในเครื่อง — เปิดเองหรือให้ Playwright เปิดให้ก็ได้)
python3 -m http.server 8000 &
BASE_URL=http://localhost:8000 npm test

npm run test:ui    # โหมด UI ของ Playwright ดูทีละสเต็ป
npm run report     # เปิดรายงาน HTML ของรันล่าสุด
```

ทั้งสองโหมด (local / prod URL) คุยกับ Firebase backend โปรเจกต์เดียวกัน (`nima-link-mvp`) ของจริง —
ต่างกันแค่ไฟล์ static ถูกเสิร์ฟจากไหน

### เปิดใช้งานไฟล์ที่ 2 ทีหลัง

เมื่อ security rules รายคอลเลกชันตาม ACL.md ขึ้นครบแล้ว ให้เอา `.fixme` ออกจาก
`test.describe.fixme(...)` ใน `acl-db.spec.js` บรรทัดแรกของ `describe` block (เปลี่ยนเป็น `test.describe(...)`)
แล้วรันใหม่ — คาดว่าจะผ่านทั้งชุด ถ้าตัวไหนยัง fail แปลว่ากฎยังไม่ครอบคลุมเคสนั้น

## บัญชีทดสอบ

ทั้งหมดรหัสผ่านเดียวกัน (ดู `TEST_PASSWORD` ใน `helpers.js`) — เป็นรหัสสมมติสำหรับบัญชีทดสอบเท่านั้น
ไม่ใช่รหัสผ่านจริงของทัช สมัครอัตโนมัติในรันแรก รันครั้งต่อไปจะเข้าสู่ระบบด้วยบัญชีเดิม (idempotent)

| อีเมล | role | channel | ใช้ทำอะไร |
|---|---|---|---|
| `e2e-buyer-otc@example.com` | buyer | OTC | ร้านหลัก — สร้าง/ดู/ลบคำขอของตัวเอง |
| `e2e-buyer-otc2@example.com` | buyer | OTC | ร้านที่สอง — ทดสอบ "ดูของร้านอื่นไม่ได้" |
| `e2e-rep-otc@example.com` | rep | OTC | ผู้แทนช่องทางเดียวกับร้านหลัก — รับ/ปฏิเสธคำขอ |
| `e2e-rep-mc@example.com` | rep | MC | ผู้แทนช่องทางอื่น — ทดสอบ "ข้ามช่องทางดูไม่ได้" |
| `e2e-role-test@example.com` | buyer | OTC | ใช้เฉพาะเทส "แก้ role ตัวเอง" ในไฟล์ที่ 2 — แยกออกมาไม่ให้กระทบบัญชีอื่นถ้ากฎหลวมจนแก้ผ่านได้จริง |

## ข้อมูลที่เทสสร้าง

คำขอ/ชื่อที่เทสสร้างขึ้นต้นด้วย `E2E-` เสมอเพื่อให้ค้นเจอง่ายและลบทิ้งได้ปลอดภัย
เทสในไฟล์ที่ 1 ลบคำขอที่สร้างไว้ท้ายเทสผ่าน UI จริง (พร้อมกล่องยืนยัน) —
เทสในไฟล์ที่ 2 (ตอนถูกเปิดใช้งานทีหลัง) เก็บกวาดข้อมูลของตัวเองแบบ best-effort หลังทุกเทส
รวมถึงกรณีที่กฎยังหลวมจนเขียนผ่านได้จริงด้วย

เก็บตกที่อาจเหลือ: ถ้าเทสถูก interrupt กลางคัน (Ctrl+C, timeout) อาจมีเอกสาร `requests`
ขึ้นต้นชื่อ/โน้ตด้วย `E2E-` ค้างอยู่ — ลบเองได้ผ่านหน้าเว็บด้วยบัญชี `e2e-buyer-otc@example.com`
(ปุ่ม "ลบคำขอนี้" ในหน้ารายละเอียด)

## ทำไมต้องแบ่ง 2 ไฟล์

ไฟล์ที่ 1 พิสูจน์ได้แค่ว่า "หน้าเว็บซ่อนปุ่ม/ข้อความให้ถูกคน" — ไม่ได้พิสูจน์ว่าใครสมัครเข้ามาแล้วยิง
query ตรงข้าม UI ไปอ่าน/เขียนของคนอื่นได้หรือไม่ ไฟล์ที่ 2 จึงข้าม UI ไปยิง Firestore ตรง ๆ
เพื่อทดสอบว่ากฎฝั่งฐานข้อมูล (`firestore.rules`) กันจริง — คนละชั้นกัน ต้องทดสอบแยกกัน
