# กฎความปลอดภัย Firestore — ที่มาของแต่ละข้อ

บันทึกของสัปดาห์ที่ 8 · ไฟล์จริงคือ `firestore.rules` ที่รากโปรเจกต์
เอกสารนี้ตอบ 3 คำถาม: กฎแต่ละข้อมาจาก **ACL ข้อไหน** · ข้อไหน **บังคับที่ชั้นนี้ไม่ได้** · และ **กระทบอะไรบ้าง**

สัปดาห์ที่ 7 มีกฎเดียวคือ "ล็อกอินก่อน" — ใครสมัครเข้ามาก็ยิง query ตรงอ่านของคนอื่นได้
สัปดาห์ที่ 8 ย้ายการกรองทั้งหมดลงมาเป็นกฎรายคอลเลกชัน

---

## หลักการที่ใช้ตลอดไฟล์

| หลัก | ทำยังไง |
|---|---|
| role / channel เชื่อถือได้แหล่งเดียว | ฟังก์ชัน `me()` อ่าน `users/{request.auth.uid}` ด้วย `get()` ฝั่งเซิร์ฟเวอร์ ไม่รับค่าจากเอกสารที่ไคลเอนต์ส่งมา จาก query string หรือ custom claims |
| OTC / MC เป็น hard gate | เทียบ `resource.data.buyerChannel` / `resource.data.channel` กับ `myChannel()` ทุกจุดที่อ่านและเขียน |
| ปิดเป็นค่าเริ่มต้น | ปิดท้ายไฟล์ด้วย `match /{document=**} { allow read, write: if false; }` คอลเลกชันที่ยังไม่ได้คิดถึงจึงไม่มีรูค้าง |
| สถานะต้องตรงกับโค้ด | `PENDING()` / `ACCEPTED()` / `REJECTED()` ในกฎ คือค่าเดียวกับ `STATUS` ใน `app/db.js` — **แก้ที่ใดที่หนึ่งต้องแก้อีกที่เสมอ** |

## ตารางกฎ → ACL

### `users/{uid}` — document id = uid จาก Firebase Auth

| กฎ | มาจาก ACL |
|---|---|
| `get` เฉพาะ `uid == request.auth.uid` | ระบบไม่มี role admin และไม่มีหน้าไหนอ่านโปรไฟล์คนอื่น |
| `list` ปิดตาย | ไม่มีหน้าไหนยิง query ทั้งคอลเลกชัน — ปิดกันไล่เก็บรายชื่อผู้ใช้ |
| `create` ต้องเป็น uid ตัวเอง + `role in ['buyer','rep']` + `channel in ['OTC','MC']` | ACL "สมัครและเข้าสู่ระบบ" · เส้นแดงข้อ 4 "ล็อกที่โปรไฟล์ตั้งแต่สมัคร" |
| `update` ห้าม `role` และ `channel` เปลี่ยนค่า | ACL ทั้งสองแถว: "เปลี่ยน role ของตัวเองไม่ได้" · เส้นแดงข้อ 4 "ไม่ใช่ช่องติ๊กให้ผู้ใช้เปลี่ยนเอง" |
| `delete` ปิดตาย | ไม่มีฟีเจอร์ลบบัญชีในขอบเขต Module 2 |

### `products/{id}`

| กฎ | มาจาก ACL |
|---|---|
| `list` ได้เฉพาะเอกสารที่ `channel == myChannel()` | ACL ร้าน "เห็นชื่อรายการยาเฉพาะช่องทางของตัวเอง" · เส้นแดงข้อ 4 |
| `get` เหมือนกัน แต่ยอมให้ `resource == null` | ผู้ช่วย AI ขั้นที่ 2 อ่าน `products/{productId}` ทีละใบ ถ้ารายการยาถูกลบไปแล้วต้องได้ "ไม่มีเอกสาร" กลับไป ไม่ใช่ `permission-denied` — เปิดเผยแค่ "ไม่มี" ไม่ได้เปิดเผยข้อมูล |
| `write` ปิดตายทุกบทบาท | ACL ร้าน "แก้ไขรายการยาในระบบไม่ได้" — ผู้แทนก็ไม่มีสิทธิ์นี้ในตาราง |

### `requests/{id}` — โฟลเดอร์หลัก

| กฎ | มาจาก ACL |
|---|---|
| `get`: เจ้าของ หรือ ผู้แทนช่องทางเดียวกัน (หรือเอกสารถูกลบไปแล้ว) | ร้าน "ดูคำขอของร้านอื่นไม่ได้" · ผู้แทน "ดูคำขอข้ามช่องทาง OTC/MC ไม่ได้" |
| `list` ข้อ 1: `isBuyer() && buyerId == uid` | ร้าน "ดูคำขอของร้านตัวเองทั้งหมด" |
| `list` ข้อ 2: `isRep() && buyerChannel == myChannel()` | ผู้แทน "ดูคำขอในช่องทางเดียวกับตัวเอง" |
| `create`: ต้อง `isBuyer()` + `buyerId == uid` + `buyerChannel == myChannel()` + `status == รอผู้แทนรับ` | ร้าน "สร้างคำขอหายา" · ผู้แทน "สร้างคำขอไม่ได้" · กันปลอมเป็นร้านอื่น · กันยัดข้ามช่องทาง · กันตั้งสถานะเองตั้งแต่ใบแรก |
| `delete`: `isBuyer() && buyerId == uid` | ร้าน "ลบคำขอของตัวเอง" / "ลบคำขอของร้านอื่นไม่ได้" · ผู้แทน "ลบคำขอไม่ได้" |
| `update` ข้อ 1: ผู้แทนช่องทางเดียวกัน + `affectedKeys().hasOnly(['status'])` + สถานะเดิมต้องเป็น `รอผู้แทนรับ` + สถานะใหม่ต้องเป็น `รับแล้ว` หรือ `ปฏิเสธ` | ผู้แทน "กดรับ / กดปฏิเสธ" · "แก้ไขช่องอื่นไม่ได้ นอกจาก `status`" · "เปลี่ยนสถานะซ้ำหลังตอบไปแล้วไม่ได้" (ไม่มีทางย้อนกลับ เพราะสถานะเดิมต้องเป็น `รอผู้แทนรับ` เท่านั้น) |
| `update` ข้อ 2: ผู้แทนช่องทางเดียวกัน + `hasOnly(['aiSuggestion','aiReason','aiUpdatedAt'])` | ช่องของผู้ช่วย AI ระดับ 2 · `hasOnly` กันไม่ให้ยัด `status` ปนมาในชุดเดียวกัน |
| **ไม่มี `allow update` ให้ `buyer` เลย** | ร้าน "เปลี่ยนสถานะคำขอไม่ได้ แม้เป็นคำขอของตัวเอง — อนุมัติของตัวเองไม่ได้" |

### `requests/{id}/replies/{id}` — ยังไม่มี UI เขียน กฎรอไว้ก่อน

| กฎ | เหตุผล |
|---|---|
| `get` / `list`: ร้านเจ้าของคำขอ หรือ ผู้แทนช่องทางเดียวกัน | อ่านจากเอกสารแม่ (`requests/{id}`) ไม่ได้อ่านจาก `resource.data` ของ reply จึงยิง `getDocs` ทั้งโฟลเดอร์ย่อยได้โดยไม่ต้องใส่ `where` — ผู้ช่วย AI ขั้นที่ 3 ยิงแบบนั้นอยู่ |
| `create`: `isRep()` + ช่องทางของคำขอแม่ตรงกับตัวเอง + `repId == uid` | ผู้แทนตอบได้เฉพาะคำขอในช่องทางตัวเอง และต้องเซ็นชื่อด้วย uid จริง |
| `update`: เจ้าของคำตอบเท่านั้น และย้าย `repId` ไม่ได้ | "แก้คำตอบของคนอื่นไม่ได้" |
| `delete`: เจ้าของคำตอบเท่านั้น | "ลบคำตอบของคนอื่นไม่ได้" |

### `requests/{id}/aiLog/{id}`

| กฎ | เหตุผล |
|---|---|
| `get` / `list`: เหมือน `replies` | บันทึกผูกกับคำขอใบนั้น คนที่เห็นคำขอได้จึงเห็นบันทึกได้ |
| `create`: `isRep()` + ช่องทางตรง + `byUid == uid` | ผู้ช่วย AI ระดับ 2 ทำงานฝั่งผู้แทนเท่านั้น |
| `update` / `delete` ปิดตาย | เป็นบันทึกไว้ตรวจย้อนหลัง แก้ได้เมื่อไหร่ก็หมดความหมาย |

## 🔴 ข้อจำกัด — สิ่งที่กฎชั้นนี้บังคับไม่ได้

### 1. เส้นแดงข้อ 5 (PDPA) — ผู้แทนยังเห็น `buyerName` ได้ก่อนกดรับ

ACL เขียนไว้ว่า *"ผู้แทนห้ามเห็นชื่อ / ที่อยู่ร้าน จนกว่าจะกดรับคำขอ — เห็นได้แค่เขต"*

**Firestore rules ซ่อนเป็น "ฟิลด์" ไม่ได้ ซ่อนได้แค่ทั้งเอกสาร**
ผู้แทนต้องอ่าน `requests/{id}` ให้ได้ตั้งแต่ก่อนกดรับ (ไม่งั้นจะไม่เห็นคำขอว่ามีอะไรให้รับ)
พอเอกสารทั้งใบส่งถึงเครื่องเขา `buyerName` ก็ติดมาด้วยเสมอ

ตอนนี้ `index.html` และ `detail.html` ปิดบังชื่อไว้ด้วย `buyerLabel()` / `revealed`
ถูกต้องในแง่หน้าจอ แต่ **เป็นการบังคับที่ชั้น UI เท่านั้น** — เปิด DevTools หรือยิง REST ตรงก็ยังเห็นชื่อ

> สถานะจริง: ข้อ 5 **ยังไม่ถูกบังคับที่ชั้นฐานข้อมูล** อย่าเขียนรายงานว่าปิดครบ

**ทางแก้จริง — งาน Sprint 2 (ยังไม่ได้ลงมือในสัปดาห์นี้ เพราะเป็นการรื้อสคีมา ไม่ใช่ขอบเขตงานเขียนกฎ)**

ย้ายข้อมูลระบุตัวตนออกไปเป็นโฟลเดอร์ย่อย แล้วล็อกทั้งเอกสารแทนการล็อกรายช่อง:

```
requests/{id}                       ← เหลือแต่ buyerArea · buyerChannel · productName · qty …
requests/{id}/identity/{doc}        ← buyerName · ที่อยู่ · เบอร์ติดต่อ
```

กฎที่ต้องเขียนคู่กัน (ร่าง):

```
match /requests/{requestId}/identity/{docId} {
  allow get: if isOwner() || (repSameChannel() && parentReq().status == ACCEPTED());
  allow write: if false;   // เขียนตอนสร้างคำขอเท่านั้น
}
```

งานที่ต้องทำพ่วงกัน: `new.html` เขียน 2 เอกสารแทน 1 · `index.html` / `detail.html` อ่าน `identity` เพิ่มเมื่อสถานะเป็น `รับแล้ว` · ย้ายข้อมูลเก่าที่มีอยู่แล้ว

### 2. `seed.html` จะเขียนข้อมูลไม่ได้อีกต่อไป — ตั้งใจให้เป็นแบบนั้น

`seed.html` เขียน 3 อย่างที่กฎใหม่ห้ามหมด:

| `seed.html` ทำอะไร | กฎใหม่ตอบว่า |
|---|---|
| `setDoc(doc(db,'users','u_shop01'), …)` | ปฏิเสธ — เขียน `users/{uid}` ได้เฉพาะ uid ของตัวเอง ไม่ใช่ id สมมติ |
| `setDoc(doc(db,'products', …))` | ปฏิเสธ — `products` `write: if false` ทุกบทบาท |
| `setDoc(doc(db,'requests','r001'), …)` | ปฏิเสธ — `buyerId` เป็น `u_shop01` ไม่ใช่ uid ของคนที่ล็อกอิน |
| `setDoc(doc(db,'requests','r002','replies','rep02'), …)` | ปฏิเสธ — `repId` เป็น `u_rep02` ไม่ใช่ uid ของคนที่ล็อกอิน |

**ไม่เจาะรูให้** — การเปิดให้ "ใครที่ล็อกอินก็เขียน `products` / `users` ได้" เพื่อให้เครื่องมือ dev ทำงาน
คือการทิ้งรูความปลอดภัยไว้ในของจริง ทางที่ถูกมี 2 ทาง:

1. รัน `seed.html` **ตอนกฎยังหลวม** (ก่อน deploy กฎชุดนี้) แล้วค่อย deploy กฎ
2. ใส่ข้อมูลตัวอย่างผ่าน **Firebase Console** — Console ใช้สิทธิ์ admin ข้าม security rules อยู่แล้ว

ข้อมูลตัวอย่างที่ seed ไว้ก่อนหน้านี้ยังอยู่ครบ กฎใหม่ห้ามเฉพาะการ **เขียนรอบใหม่**

### 3. สลับ `role` เป็น `rep` เพื่อทดสอบ ต้องทำผ่าน Firebase Console

`CLAUDE.md` แนะให้สลับ `role` ของบัญชีตัวเองใน Firestore เป็น `rep` เพื่อทดสอบปุ่มฝั่งผู้แทน
ตั้งแต่นี้ไปหน้าเว็บทำไม่ได้แล้ว (กฎ `users` ห้าม `role` / `channel` เปลี่ยนค่าตอน `update`)
ให้แก้จาก **Firebase Console** แทน — Console ข้าม rules ได้ วิธีทดสอบยังใช้ได้เหมือนเดิม

### 4. หน้าเว็บยังไม่รองรับ `permission-denied` ทุกจุด (ส่งต่อให้เจ้าของไฟล์ UI)

`detail.html` → `load()` เรียก `getDoc(ref)` โดยไม่มี `try/catch`
เดิมถ้าร้านเปิด `detail.html?id=` ของร้านอื่น จะอ่านเอกสารได้แล้วหน้าเว็บขึ้นว่า "คำขอใบนี้เป็นของร้านอื่น"
ตั้งแต่มีกฎชุดนี้ Firestore จะโยน `permission-denied` ตั้งแต่ชั้นฐานข้อมูล — **ปลอดภัยกว่าเดิม** แต่หน้าจอจะค้างที่ "กำลังโหลด..."
เกิดเฉพาะกรณีแก้ URL เองเท่านั้น ไม่มีปุ่มไหนในระบบพาไปถึง
เป็นงานเก็บตกฝั่ง UI ไม่ใช่งานของไฟล์กฎ — **ไม่ได้แก้ในรอบนี้เพราะอยู่นอกขอบเขตไฟล์ที่รับผิดชอบ**

## ผลของกฎต่อ query ทุกตัวในเว็บ

ไล่ทีละบรรทัดจาก `index.html` · `new.html` · `detail.html` · `app/auth.js`

| ที่ไหน | คำสั่ง | กฎที่รับ | ผล |
|---|---|---|---|
| `index.html` (ร้าน) | `where("buyerId","==",me.uid)` | `requests` `list` ข้อ 1 | ผ่าน — ไม่ต้องแก้ |
| `index.html` (ผู้แทน) | `where("buyerChannel","==",me.channel)` | `requests` `list` ข้อ 2 | ผ่าน — ไม่ต้องแก้ |
| `new.html` | `where("channel","==",me.channel)` บน `products` | `products` `list` | ผ่าน |
| `new.html` | `addDoc(requests, …)` | `requests` `create` | ผ่าน — โค้ดใส่ `buyerId`/`buyerChannel`/`status` ตรงเงื่อนไขอยู่แล้ว |
| `detail.html` | `getDoc(requests/{id})` | `requests` `get` | ผ่านเมื่อเป็นเจ้าของหรือผู้แทนช่องทางเดียวกัน · นอกนั้นถูกปฏิเสธ **ตามที่ต้องการ** |
| `detail.html` AI ขั้น 2 | `getDoc(products/{productId})` | `products` `get` | ผ่าน — รายการยาที่เลือกตอนสร้างคำขอย่อมอยู่ช่องทางเดียวกับร้านเสมอ |
| `detail.html` AI ขั้น 3 | `getDocs(requests/{id}/replies)` | `replies` `list` | ผ่าน — กฎอ่านจากเอกสารแม่ ไม่บังคับให้ใส่ `where` |
| `detail.html` AI ขั้น 4 | **แก้แล้ว** | `requests` `list` ข้อ 2 | เดิม `where("productId","==",…)` → โดนปฏิเสธทั้ง query เพราะไม่มีเงื่อนไขช่องทาง |
| `detail.html` | `updateDoc(ref,{aiSuggestion,aiReason,aiUpdatedAt})` | `requests` `update` ข้อ 2 | ผ่าน |
| `detail.html` | `addDoc(requests/{id}/aiLog, …)` | `aiLog` `create` | ผ่าน — โค้ดใส่ `byUid: me.uid` อยู่แล้ว |
| `detail.html` | `updateDoc(ref,{status})` | `requests` `update` ข้อ 1 | ผ่านครั้งเดียว — กดซ้ำใบเดิมถูกปฏิเสธที่ชั้นฐานข้อมูล |
| `detail.html` | `deleteDoc(ref)` | `requests` `delete` | ผ่านเฉพาะร้านเจ้าของ |
| `app/auth.js` | `setDoc(users/{uid}, …)` | `users` `create` / `update` | ผ่าน — id คือ uid ของตัวเอง · การ retry ตอนสมัครยังทำงานเหมือนเดิม |
| `app/auth.js` | `getDoc(users/{uid})` | `users` `get` | ผ่าน — อ่านของตัวเองเท่านั้น |

### query เดียวที่ถูกแก้

`detail.html` ผู้ช่วย AI ขั้นที่ 4:

```js
// เดิม — ไม่มีเงื่อนไขช่องทาง กฎ list ปฏิเสธทั้ง query
query(collection(db, "requests"), where("productId", "==", r.productId))

// ใหม่ — กรองด้วย where ตัวเดียว แล้วคัด productId + status ฝั่งหน้าเว็บ
query(collection(db, "requests"), where("buyerChannel", "==", me.channel))
```

เลือกทางนี้เพราะตรงรูปกฎ `list` พอดี และเลี่ยง composite index ตามสำนวนเดิมของโปรเจกต์
("กรองด้วย `where` ตัวเดียวแล้วเรียงฝั่งหน้าเว็บ") ผลลัพธ์ที่ AI เห็นเหมือนเดิมทุกประการ
เพราะโค้ดเดิมก็กรอง `buyerChannel` กับ `status` ฝั่งหน้าเว็บอยู่แล้ว

## ตรวจแล้วแค่ไหน

| ตรวจอะไร | ผล |
|---|---|
| ไวยากรณ์กฎ · `firebase deploy --only firestore:rules --dry-run` | ✅ `rules file firestore.rules compiled successfully` · `Dry run complete!` (ไม่ได้ deploy ของจริง) |
| ไล่สายตาทุก query ใน 3 หน้า + `app/auth.js` | ✅ ตารางข้างบน |
| ทดสอบพฤติกรรมจริงของกฎ | ⛔ **ยังไม่ได้ทำ** — โปรเจกต์นี้ไม่มี emulator และไม่ลง dependency เพิ่ม |

การพิสูจน์จริงต้องมาจาก **Playwright E2E** ที่เพื่อนร่วมทีมทำอยู่ใน `tests/`
เคสที่ต้องครอบให้ครบอย่างน้อย:

1. ร้าน A เปิด `detail.html?id=` ของคำขอร้าน B → ต้องไม่ได้ข้อมูล
2. ร้านเจ้าของยิง `updateDoc` เปลี่ยน `status` เอง → ต้องโดนปฏิเสธ
3. ผู้แทน OTC เห็นเฉพาะคำขอ OTC · ยิงอ่าน MC ตรง → โดนปฏิเสธ
4. ผู้แทนกดรับคำขอเดิมซ้ำครั้งที่สอง → โดนปฏิเสธ
5. ผู้แทนยิง `updateDoc` แก้ `qty` หรือ `note` → โดนปฏิเสธ
6. ผู้แทนยิง `updateDoc` ที่มี `aiSuggestion` + `status` มาด้วยกัน → โดนปฏิเสธ
7. ผู้แทนยิง `addDoc` สร้างคำขอ / `deleteDoc` ลบคำขอ → โดนปฏิเสธ
8. ผู้ใช้แก้ `role` ของตัวเองจากหน้าเว็บ → โดนปฏิเสธ
9. ใครก็ตามเขียน `products` → โดนปฏิเสธ

> ⚠️ กฎชุดนี้ยังไม่ได้ deploy ขึ้นของจริง
> คำสั่งตอน deploy คือ `npx firebase-tools deploy --only hosting,firestore:rules`
> **ห้าม deploy เว็บโดยไม่ deploy กฎไปพร้อมกัน** — โค้ดกับกฎรอบนี้แก้คู่กัน
> ถ้า deploy แต่กฎโดยไม่ deploy เว็บ ผู้ช่วย AI ขั้นที่ 4 ที่ยังเป็น query เก่าจะพังทันที
