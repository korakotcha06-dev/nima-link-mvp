# กฎความปลอดภัย Firestore — ที่มาของแต่ละข้อ

บันทึกของสัปดาห์ที่ 8 · ไฟล์จริงคือ `firestore.rules` ที่รากโปรเจกต์
เอกสารนี้ตอบ 3 คำถาม: กฎแต่ละข้อมาจาก **ACL ข้อไหน** · ข้อไหน **บังคับที่ชั้นนี้ไม่ได้** · และ **กระทบอะไรบ้าง**

สัปดาห์ที่ 7 มีกฎเดียวคือ "ล็อกอินก่อน" — ใครสมัครเข้ามาก็ยิง query ตรงอ่านของคนอื่นได้
สัปดาห์ที่ 8 ย้ายการกรองทั้งหมดลงมาเป็นกฎรายคอลเลกชัน

| รอบ | ทำอะไร |
|---|---|
| รอบที่ 1 | เขียนกฎรายคอลเลกชันให้ตรงตาราง `ACL.md` ทั้งใบ |
| รอบที่ 2 | ดึงงาน PDPA จาก Sprint 2 ขึ้นมาทำ — ย้าย `buyerName` ออกจากเอกสารคำขอ + เพิ่ม `acceptedBy` |

## หลักการที่ใช้ตลอดไฟล์

| หลัก | ทำยังไง |
|---|---|
| role / channel เชื่อถือได้แหล่งเดียว | ฟังก์ชัน `me()` อ่าน `users/{request.auth.uid}` ด้วย `get()` ฝั่งเซิร์ฟเวอร์ ไม่รับค่าจากเอกสารที่ไคลเอนต์ส่งมา จาก query string หรือ custom claims |
| OTC / MC เป็น hard gate | เทียบ `resource.data.buyerChannel` / `resource.data.channel` กับ `myChannel()` ทุกจุดที่อ่านและเขียน |
| ปิดเป็นค่าเริ่มต้น | ปิดท้ายไฟล์ด้วย `match /{document=**} { allow read, write: if false; }` คอลเลกชันที่ยังไม่ได้คิดถึงจึงไม่มีรูค้าง |
| สถานะต้องตรงกับโค้ด | `PENDING()` / `ACCEPTED()` / `REJECTED()` ในกฎ คือค่าเดียวกับ `STATUS` ใน `app/db.js` — **แก้ที่ใดที่หนึ่งต้องแก้อีกที่เสมอ** |

## ตารางกฎ → ACL

### `users/{uid}` — document id = uid จาก Firebase Auth

| กฎ | มาจาก ACL |
|---|---|
| `get` เฉพาะ `uid == request.auth.uid` | ระบบไม่มี role admin และไม่มีหน้าไหนอ่านโปรไฟล์คนอื่น |
| `list` ปิดตาย | ไม่มีหน้าไหนยิง query ทั้งคอลเลกชัน — ปิดกันไล่เก็บรายชื่อผู้ใช้ |
| `create` ต้องเป็น uid ตัวเอง + `role in ['buyer','rep']` + `channel in ['OTC','MC']` | ACL "สมัครและเข้าสู่ระบบ" · เส้นแดงข้อ 4 "ล็อกที่โปรไฟล์ตั้งแต่สมัคร" |
| `update` ห้าม `role` และ `channel` เปลี่ยนค่า | ACL ทั้งสองแถว: "เปลี่ยน role ของตัวเองไม่ได้" · เส้นแดงข้อ 4 "ไม่ใช่ช่องติ๊กให้ผู้ใช้เปลี่ยนเอง" |
| `delete` ปิดตาย | ไม่มีฟีเจอร์ลบบัญชีในขอบเขต Module 2 |

### `products/{id}`

| กฎ | มาจาก ACL |
|---|---|
| `list` ได้เฉพาะเอกสารที่ `channel == myChannel()` | ACL ร้าน "เห็นชื่อรายการยาเฉพาะช่องทางของตัวเอง" · เส้นแดงข้อ 4 |
| `get` เหมือนกัน แต่ยอมให้ `resource == null` | ผู้ช่วย AI ขั้นที่ 2 อ่าน `products/{productId}` ทีละใบ ถ้ารายการยาถูกลบไปแล้วต้องได้ "ไม่มีเอกสาร" กลับไป ไม่ใช่ `permission-denied` — เปิดเผยแค่ "ไม่มี" ไม่ได้เปิดเผยข้อมูล |
| `write` ปิดตายทุกบทบาท | ACL ร้าน "แก้ไขรายการยาในระบบไม่ได้" — ผู้แทนก็ไม่มีสิทธิ์นี้ในตาราง |

### `requests/{id}` — โฟลเดอร์หลัก

| กฎ | มาจาก ACL |
|---|---|
| `get`: เจ้าของ หรือ ผู้แทนช่องทางเดียวกัน (หรือเอกสารถูกลบไปแล้ว) | ร้าน "ดูคำขอของร้านอื่นไม่ได้" · ผู้แทน "ดูคำขอข้ามช่องทาง OTC/MC ไม่ได้" |
| `list` ข้อ 1: `isBuyer() && buyerId == uid` | ร้าน "ดูคำขอของร้านตัวเองทั้งหมด" |
| `list` ข้อ 2: `isRep() && buyerChannel == myChannel()` | ผู้แทน "ดูคำขอในช่องทางเดียวกับตัวเอง" |
| `create`: ต้อง `isBuyer()` + `buyerId == uid` + `buyerChannel == myChannel()` + `status == รอผู้แทนรับ` + **ห้ามมีช่อง `buyerName` และ `acceptedBy`** | ร้าน "สร้างคำขอหายา" · ผู้แทน "สร้างคำขอไม่ได้" · กันปลอมเป็นร้านอื่น · กันยัดข้ามช่องทาง · กันตั้งสถานะเองตั้งแต่ใบแรก · เส้นแดงข้อ 5 บังคับที่ชั้นฐานข้อมูลว่าชื่อร้านห้ามอยู่บนเอกสารคำขอ |
| `delete`: `isBuyer() && buyerId == uid` | ร้าน "ลบคำขอของตัวเอง" / "ลบคำขอของร้านอื่นไม่ได้" · ผู้แทน "ลบคำขอไม่ได้" |
| `update` ข้อ 1: ผู้แทนช่องทางเดียวกัน + `affectedKeys().hasOnly(['status','acceptedBy'])` + สถานะเดิมต้องเป็น `รอผู้แทนรับ` + **กดรับ → `acceptedBy` ต้องเท่ากับ uid ตัวเอง** · **กดปฏิเสธ → ห้ามแตะ `acceptedBy` เลย** | ผู้แทน "กดรับ / กดปฏิเสธ" · "แก้ไขช่องอื่นไม่ได้ นอกจาก `status`" · "เปลี่ยนสถานะซ้ำหลังตอบไปแล้วไม่ได้" (ไม่มีทางย้อนกลับ เพราะสถานะเดิมต้องเป็น `รอผู้แทนรับ` เท่านั้น) · `acceptedBy` คือตัวที่ตอบว่า "ใคร" กดรับ — ยกให้คนอื่นรับแทนไม่ได้ |
| `update` ข้อ 2: ผู้แทนช่องทางเดียวกัน + `hasOnly(['aiSuggestion','aiReason','aiUpdatedAt'])` | ช่องของผู้ช่วย AI ระดับ 2 · `hasOnly` กันไม่ให้ยัด `status` ปนมาในชุดเดียวกัน |
| **ไม่มี `allow update` ให้ `buyer` เลย** | ร้าน "เปลี่ยนสถานะคำขอไม่ได้ แม้เป็นคำขอของตัวเอง — อนุมัติของตัวเองไม่ได้" |

### `requests/{id}/identity/buyer` — 🔴 หัวใจของเส้นแดงข้อ 5

ชื่อร้านถูก **ยกออกจากเอกสารคำขอ** มาไว้ที่นี่ เพราะ Firestore ล็อกได้ทีละ "เอกสาร" ไม่ใช่ทีละ "ฟิลด์"
doc id ตายตัวว่า `buyer` หน้าเว็บจึง `getDoc` ตรงได้ ไม่ต้อง `list`
`buyerArea` **ยังอยู่บนเอกสารคำขอตามเดิม** — ACL ให้ผู้แทนเห็น "เขต" ได้ก่อนกดรับ

| กฎ | มาจาก ACL |
|---|---|
| `get`: ร้านเจ้าของคำขอ **หรือ** ผู้แทนที่ `parent.status == 'รับแล้ว'` **และ** `parent.acceptedBy == uid` | ACL ผู้แทน "เห็นชื่อและเขตของร้าน**หลังกดรับแล้วเท่านั้น**" — เงื่อนไขสองท่อนพร้อมกัน ทั้ง "รับแล้ว" และ "คนที่รับคือคุณ" |
| `list`: `if false` | ไม่มีหน้าไหนต้องไล่อ่านทั้งโฟลเดอร์ย่อย |
| `create`: `isBuyer()` + `getAfter(requests/{id}).data.buyerId == uid` | เขียนพร้อมเอกสารคำขอใน `writeBatch` ก้อนเดียว ดูหมายเหตุ `getAfter` ข้างล่าง |
| `update` / `delete`: ร้านเจ้าของคำขอเท่านั้น | ผู้แทนแตะชื่อร้านไม่ได้ทั้งการแก้และการลบ |

**ทำไมต้อง `getAfter` ไม่ใช่ `get`**
`new.html` เขียนเอกสารคำขอกับ `identity/buyer` ใน `writeBatch` ก้อนเดียวเพื่อให้ atomic
แต่ตอนกฎของ `identity/buyer` ทำงาน เอกสารแม่ในก้อนเดียวกัน **ยังไม่ commit** — `get()` จะเห็นสถานะ *ก่อน* ก้อนนี้
คือยังไม่มีเอกสารแม่ แล้วปฏิเสธทั้งที่คำขอถูกต้องทุกอย่าง
`getAfter()` อ่าน "สภาพหลังก้อนนี้ commit" จึงตรวจความเป็นเจ้าของได้จริง
ถ้าเรียกนอก batch (เอกสารแม่มีอยู่แล้ว) `getAfter()` คืนค่าปัจจุบัน ผลเหมือน `get()` ทุกประการ

> ⚠️ `getAfter` ผ่านแค่ขั้นคอมไพล์ **ยังไม่ได้พิสูจน์ตอนรันจริง** เพราะโปรเจกต์นี้ไม่มี emulator
> เคสที่ Playwright ต้องยืนยันคือ "ร้านกดส่งคำขอใหม่แล้ว `identity/buyer` เกิดขึ้นจริงพร้อมเอกสารคำขอ"
> ถ้าเคสนี้ไม่ผ่าน แปลว่าต้องกลับมาคุยเรื่องแบบ — **อย่าแก้ด้วยการผ่อนกฎ `create` ให้หลวมลงเอง**

### `requests/{id}/replies/{id}` — ยังไม่มี UI เขียน กฎรอไว้ก่อน

| กฎ | เหตุผล |
|---|---|
| `get` / `list`: ร้านเจ้าของคำขอ หรือ ผู้แทนช่องทางเดียวกัน | อ่านจากเอกสารแม่ (`requests/{id}`) ไม่ได้อ่านจาก `resource.data` ของ reply จึงยิง `getDocs` ทั้งโฟลเดอร์ย่อยได้โดยไม่ต้องใส่ `where` — ผู้ช่วย AI ขั้นที่ 3 ยิงแบบนั้นอยู่ |
| `create`: `isRep()` + ช่องทางของคำขอแม่ตรงกับตัวเอง + `repId == uid` | ผู้แทนตอบได้เฉพาะคำขอในช่องทางตัวเอง และต้องเซ็นชื่อด้วย uid จริง |
| `update`: เจ้าของคำตอบเท่านั้น และย้าย `repId` ไม่ได้ | "แก้คำตอบของคนอื่นไม่ได้" |
| `delete`: เจ้าของคำตอบเท่านั้น | "ลบคำตอบของคนอื่นไม่ได้" |

### `requests/{id}/aiLog/{id}`

| กฎ | เหตุผล |
|---|---|
| `get` / `list`: เหมือน `replies` | บันทึกผูกกับคำขอใบนั้น คนที่เห็นคำขอได้จึงเห็นบันทึกได้ |
| `create`: `isRep()` + ช่องทางตรง + `byUid == uid` | ผู้ช่วย AI ระดับ 2 ทำงานฝั่งผู้แทนเท่านั้น |
| `update` / `delete` ปิดตาย | เป็นบันทึกไว้ตรวจย้อนหลัง แก้ได้เมื่อไหร่ก็หมดความหมาย |

## 🔴 ข้อจำกัด และงานที่ยังค้าง

### 1. เส้นแดงข้อ 5 (PDPA) — ปิดแล้วที่ชั้นฐานข้อมูล เหลืองานล้างข้อมูลเก่า

> รอบแรกข้อนี้ยัง "บังคับได้แค่ชั้น UI" · รอบที่สอง (Sprint 2 ดึงขึ้นมาทำ) ย้ายสคีมาจริงแล้ว

ปิดไป **2 ปัญหา** ไม่ใช่ข้อเดียว:

**P1 — `buyerName` ติดไปกับ payload เสมอ**
ผู้แทนต้องอ่าน `requests/{id}` ให้ได้ตั้งแต่ก่อนกดรับ (ไม่งั้นจะไม่เห็นว่ามีคำขออะไรให้รับ)
พอเอกสารทั้งใบถึงเครื่องเขา ชื่อร้านก็ติดไปด้วย ต่อให้หน้าจอปิดบังไว้ เปิด DevTools ก็เห็น
→ **แก้โดยย้าย `buyerName` ออกไป `requests/{id}/identity/buyer`** ซึ่งล็อกได้ทั้งเอกสาร
เอกสารคำขอเหลือแค่ `buyerArea` ตามที่ ACL อนุญาต

**P2 — `revealed` ไม่ได้ถามว่า "ใคร" เป็นคนกดรับ**
ตรรกะเดิมคือ `revealed = isBuyer || r.status === 'รับแล้ว'`
พอผู้แทนคนหนึ่งกดรับ **ผู้แทนคนอื่นทั้งช่องทางก็เห็นชื่อร้านตามไปด้วย**
ผิด ACL ที่เขียนว่า "เห็นชื่อและเขตของร้านหลังกดรับแล้วเท่านั้น" (หมายถึงคนที่กดรับ)
สคีมาเดิมไม่มีช่องบันทึกว่าใครรับ จึงกันไม่ได้แม้อยากกัน
→ **แก้โดยเพิ่มช่อง `acceptedBy`** บน `requests/{id}` เขียนพร้อม `status` ในคำสั่งเดียว
แล้วให้กฎของ `identity/buyer` ถามทั้ง `status == 'รับแล้ว'` และ `acceptedBy == uid`
`index.html` กับ `detail.html` แก้ตรรกะตามทั้งคู่ (ฟังก์ชัน `revealedToMe`)

สรุปสภาพตอนนี้ของแต่ละสายตา:

| ใคร | เห็นอะไรบนเอกสารคำขอ | อ่าน `identity/buyer` ได้ไหม |
|---|---|---|
| ร้านเจ้าของ | ทุกช่อง | ได้ (แต่หน้าเว็บใช้ `me.name` จากโปรไฟล์ ไม่ต้องยิง) |
| ร้านอื่น | ไม่เห็นเอกสารเลย | ไม่ได้ |
| ผู้แทนช่องทางเดียวกัน ยังไม่กดรับ | เห็น **เขต** ไม่มีชื่อร้านให้เห็นตั้งแต่ต้นทาง | **ไม่ได้** |
| ผู้แทนคนที่กดรับใบนั้น | เห็นเขต | **ได้** |
| ผู้แทนคนอื่น หลังเพื่อนกดรับไปแล้ว | เห็นเขต | **ไม่ได้** ← P2 ที่เพิ่งปิด |
| ผู้แทนคนละช่องทาง | ไม่เห็นเอกสารเลย | ไม่ได้ |

#### 🔴 ยังไม่จบ — ข้อมูลเก่าที่ค้างอยู่ ต้องล้างด้วยมือ

**การแก้โค้ดไม่ได้ลบ `buyerName` ออกจากเอกสารที่เขียนไปแล้ว** คำขอเดิมทุกใบยังมีช่องนี้ติดอยู่
ตราบใดที่ยังไม่ล้าง รูของ P1 **ยังเปิดอยู่กับข้อมูลเก่า** (ยิง REST อ่านเอกสารคำขอก็ยังได้ชื่อร้านกลับมา)

สิ่งที่ทำไปแล้วฝั่งโค้ด: ทุกหน้า **ทิ้ง `buyerName` ทิ้งตั้งแต่บรรทัดที่รับข้อมูลมา**
(`const { buyerName, ...rest } = d.data()`) และ **ไม่มี fallback ไปหยิบของเก่ามาโชว์** —
ถ้าไม่มี `identity/buyer` ก็แสดงว่า "ยังไม่เปิดเผยชื่อ" ไปเลย ไม่งั้นเท่ากับรูยังเปิด

สิ่งที่ **ต้องทำด้วยมือ ก่อนถือว่าปิดรูสำเร็จ**:

1. เปิด Firebase Console → Firestore → คอลเลกชัน `requests`
2. ลบช่อง `buyerName` ออกจากเอกสารเดิมทุกใบ
3. ใบที่สถานะเป็น `รับแล้ว` ให้เติม `acceptedBy` ให้ตรงกับผู้แทนที่รับจริง ไม่งั้นแม้แต่คนที่รับก็จะไม่เห็นชื่อร้าน
4. สร้าง `requests/{id}/identity/buyer` ให้เอกสารเดิมทุกใบ ไม่งั้นชื่อร้านของคำขอเก่าจะหายไปเฉย ๆ

> ข้อมูลในระบบตอนนี้เป็น **ชื่อสมมติทั้งหมด** ความเสี่ยงจริงจึงต่ำ
> แต่ต้องล้างให้เสร็จก่อนเอาข้อมูลจริงเข้าระบบ — ตรงกับเส้นแดงข้อ 6
> ทางลัดที่เร็วกว่าคือลบคำขอตัวอย่างทิ้งแล้วรัน `seed.html` ชุดใหม่ (ดูข้อจำกัดข้อ 2)

#### ค้างไว้เป็นงาน Sprint ถัดไป — ลบคำขอแล้ว subcollection ไม่หายตาม

**Firestore ไม่มี cascade delete** ลบ `requests/{id}` แล้ว `identity/buyer` · `replies/*` · `aiLog/*`
**ยังอยู่ครบ** กลายเป็นเอกสารกำพร้าที่ไม่มีใครอ่านถึง (กฎ `get` ของ `identity` ต้องอ่านเอกสารแม่ก่อน
พอแม่หายก็ error → ปฏิเสธ) — ปลอดภัยในแง่สิทธิ์ แต่เป็น **ขยะที่ยังเก็บชื่อร้านไว้จริง ๆ ในฐานข้อมูล**
และยังกินโควตา

ปิดจริงได้ 2 ทาง เลือกใน Sprint ถัดไป:

- **Cloud Function** `onDocumentDeleted('requests/{id}')` ไล่ลบ subcollection ทั้งหมด (ทางมาตรฐาน แต่ต้องขึ้น Blaze plan)
- **ให้หน้าเว็บลบเป็นชุด** — `detail.html` ลบ `identity/buyer` + `replies` + `aiLog` ก่อนแล้วค่อยลบเอกสารแม่
  (ไม่การันตี ถ้าปิดแท็บกลางคันก็ค้างอยู่ดี และต้องเปิดสิทธิ์ `list` ให้ร้านเจ้าของเพิ่ม)

**รอบนี้ยังไม่ได้ทำทั้งสองทาง** — `detail.html` ยังลบเฉพาะเอกสารแม่เหมือนเดิม

### 2. `seed.html` จะเขียนข้อมูลไม่ได้อีกต่อไป — ตั้งใจให้เป็นแบบนั้น

`seed.html` เขียนของที่กฎใหม่ห้ามหมดทุกบรรทัด:

| `seed.html` ทำอะไร | กฎใหม่ตอบว่า |
|---|---|
| `setDoc(doc(db,'users','u_shop01'), …)` | ปฏิเสธ — เขียน `users/{uid}` ได้เฉพาะ uid ของตัวเอง ไม่ใช่ id สมมติ |
| `setDoc(doc(db,'products', …))` | ปฏิเสธ — `products` `write: if false` ทุกบทบาท |
| `setDoc(doc(db,'requests','r001'), …)` | ปฏิเสธ — `buyerId` เป็น `u_shop01` ไม่ใช่ uid ของคนที่ล็อกอิน |
| `setDoc(doc(db,'requests','r001','identity','buyer'), …)` | ปฏิเสธ — `getAfter` บนเอกสารแม่ให้ `buyerId` เป็น `u_shop01` ไม่ตรง uid |
| `setDoc(doc(db,'requests','r002','replies','rep02'), …)` | ปฏิเสธ — `repId` เป็น `u_rep02` ไม่ใช่ uid ของคนที่ล็อกอิน |

**รอบนี้ `seed.html` ถูกแก้ตามสคีมาใหม่แล้ว** (ยังเขียนไม่ผ่านกฎเหมือนเดิม แต่โครงข้อมูลตรง):
- เลิกเขียน `buyerName` ลงเอกสารคำขอ
- เขียน `requests/{id}/identity/buyer` ให้คำขอตัวอย่าง **ทุกใบ**
- ใบ `r002` ที่สถานะ `รับแล้ว` ใส่ `acceptedBy: "u_rep02"` ให้ตรงกับผู้แทนที่เขียน `replies` ไว้
  (ถ้าไม่ใส่ จะไม่มีใครเห็นชื่อร้านของใบนี้ได้เลย แม้แต่คนที่ "รับ" ไปแล้ว)

**ไม่เจาะรูให้** — การเปิดให้ "ใครที่ล็อกอินก็เขียน `products` / `users` ได้" เพื่อให้เครื่องมือ dev ทำงาน
คือการทิ้งรูความปลอดภัยไว้ในของจริง ทางที่ถูกมี 2 ทาง:

1. รัน `seed.html` **ตอนกฎยังหลวม** (ก่อน deploy กฎชุดนี้) แล้วค่อย deploy กฎ
2. ใส่ข้อมูลตัวอย่างผ่าน **Firebase Console** — Console ใช้สิทธิ์ admin ข้าม security rules อยู่แล้ว

ข้อมูลตัวอย่างที่ seed ไว้ก่อนหน้านี้ยังอยู่ครบ กฎใหม่ห้ามเฉพาะการ **เขียนรอบใหม่**

### 3. สลับ `role` เป็น `rep` เพื่อทดสอบ ต้องทำผ่าน Firebase Console

`CLAUDE.md` แนะให้สลับ `role` ของบัญชีตัวเองใน Firestore เป็น `rep` เพื่อทดสอบปุ่มฝั่งผู้แทน
ตั้งแต่นี้ไปหน้าเว็บทำไม่ได้แล้ว (กฎ `users` ห้าม `role` / `channel` เปลี่ยนค่าตอน `update`)
ให้แก้จาก **Firebase Console** แทน — Console ข้าม rules ได้ วิธีทดสอบยังใช้ได้เหมือนเดิม

### 4. หน้าเว็บยังไม่รองรับ `permission-denied` ทุกจุด (ส่งต่อให้เจ้าของไฟล์ UI)

`detail.html` → `load()` เรียก `getDoc(ref)` โดยไม่มี `try/catch`
เดิมถ้าร้านเปิด `detail.html?id=` ของร้านอื่น จะอ่านเอกสารได้แล้วหน้าเว็บขึ้นว่า "คำขอใบนี้เป็นของร้านอื่น"
ตั้งแต่มีกฎชุดนี้ Firestore จะโยน `permission-denied` ตั้งแต่ชั้นฐานข้อมูล — **ปลอดภัยกว่าเดิม** แต่หน้าจอจะค้างที่ "กำลังโหลด..."
เกิดเฉพาะกรณีแก้ URL เองเท่านั้น ไม่มีปุ่มไหนในระบบพาไปถึง
เป็นงานเก็บตกฝั่ง UI ไม่ใช่งานของไฟล์กฎ — **ไม่ได้แก้ในรอบนี้เพราะอยู่นอกขอบเขตไฟล์ที่รับผิดชอบ**

### query / คำสั่งเขียน ที่ถูกแก้เพราะกฎบังคับ

**1. `detail.html` ผู้ช่วย AI ขั้นที่ 4** (รอบแรก)

```js
// เดิม — ไม่มีเงื่อนไขช่องทาง กฎ list ปฏิเสธทั้ง query
query(collection(db, "requests"), where("productId", "==", r.productId))

// ใหม่ — กรองด้วย where ตัวเดียว แล้วคัด productId + status ฝั่งหน้าเว็บ
query(collection(db, "requests"), where("buyerChannel", "==", me.channel))
```

เลือกทางนี้เพราะตรงรูปกฎ `list` พอดี และเลี่ยง composite index ตามสำนวนเดิมของโปรเจกต์
("กรองด้วย `where` ตัวเดียวแล้วเรียงฝั่งหน้าเว็บ") ผลลัพธ์ที่ AI เห็นเหมือนเดิมทุกประการ
เพราะโค้ดเดิมก็กรอง `buyerChannel` กับ `status` ฝั่งหน้าเว็บอยู่แล้ว

**2. `new.html` ตอนกดส่งคำขอ** (รอบสอง)

```js
// เดิม — ชื่อร้านอยู่บนเอกสารคำขอ ผู้แทนทุกคนในช่องทางอ่านได้
await addDoc(collection(db, "requests"), { …, buyerName: me.name, … });

// ใหม่ — สองเอกสาร จบในก้อนเดียว
const ref = doc(collection(db, "requests"));          // สร้าง id ล่วงหน้า
const batch = writeBatch(db);
batch.set(ref, { … ไม่มี buyerName … });
batch.set(doc(db, "requests", ref.id, "identity", "buyer"), { buyerName: me.name });
await batch.commit();
```

ต้องเป็น `writeBatch` ไม่ใช่ `addDoc` แล้วตามด้วย `setDoc` สองจังหวะ —
ถ้าจังหวะสองพัง จะได้คำขอที่ไม่มีชื่อร้านค้างในระบบ ผู้แทนรับไปก็ติดต่อใครไม่ได้ และกู้คืนไม่ได้

**3. `detail.html` ตอนกดรับ** (รอบสอง) — `updateDoc(ref, { status, acceptedBy: me.uid })`
เขียนสองช่องในคำสั่งเดียวเพราะกฎบังคับให้มาคู่กัน · ตอนกดปฏิเสธเขียน `{ status }` อย่างเดียว

**4. `index.html` + `detail.html` ตรรกะเปิดเผยชื่อ** (รอบสอง)

```js
// เดิม — ถามแค่ว่า "รับแล้วหรือยัง"
const revealed = isBuyer || r.status === STATUS.ACCEPTED;

// ใหม่ — ถามว่า "คนที่รับคือเราหรือเปล่า" แล้วค่อยไปอ่าน identity/buyer
const revealedToMe = !isBuyer && r.status === STATUS.ACCEPTED && r.acceptedBy === me.uid;
```

ทั้งสองหน้า **ทิ้ง `buyerName` ของเอกสารเก่าตั้งแต่บรรทัดที่รับข้อมูล** ด้วย
`const { buyerName, ...rest } = d.data()` — ไม่มีทางหลุดขึ้นจอแม้ข้อมูลเก่าจะยังมีช่องนี้ค้างอยู่

10. 🔴 **ผู้แทน ก กดรับคำขอ แล้วผู้แทน ข ในช่องทางเดียวกันต้องยังไม่เห็นชื่อร้าน** —
